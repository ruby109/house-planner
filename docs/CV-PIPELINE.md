# M4-CV 混合识别 —— 设计规格

> **⚠️ M5 架构裁定（2026-08-11，用户决策；2026-08-12 实现完毕；M5.1 墙网闭合见第 9 节）**：放弃「VLM 出几何」的一切路径。
> **几何唯一来源 = OpenCV**（墙/房间/门窗洞口/柱），**AI 只做房间标注**（对 CV 分出的区域按编号回答
> 名称/地面类型/帖数，不输出任何坐标）。CV 提取不达标时**直接报错并引导手动描图**，
> 不再回退「AI 画几何」。**当前架构见第 8 节**；第 3~6 节描述的 M4 融合器（`hybrid` 管线）
> 仍留在代码与 API 里供对比，但已从 UI 移除。

> v2 路线：OpenCV 提取精确墙体几何，VLM 只管语义（房间名/帖数/门窗/柱），融合器合成最终文档。
> 算法基础：FloorplanToBlender3d（GPL-3.0）的管线设计，**清洁重写**为 TS + opencv.js（不引用其代码，避免 GPL 传染）。
> 运行时：`@techstark/opencv-js`（官方 WASM 打包，Node/浏览器通吃）；图片解码用纯 JS 的 jpeg-js + pngjs（不引原生依赖）。

## 1. 分层

```

  pipeline.ts               总入口 extractGeometry(image, opts) → CvExtract
  binarize.ts               双模式二值化 + deskew
  wallMask.ts               粗线筛选 + 文字剔除 + 虚线/细线框剔除（M4.1）
  dashFilter.ts             虚线链聚类 + 「整块比墙细」判定（纯 TS，M4.1）
  islandFilter.ts           孤岛墙段剔除（纯 TS，M4.1）
  skeleton.ts               Zhang-Suen 细化（纯 TS，~50 行）
  segments.ts               HoughLinesP → 角度量化 → 共线合并 → 端点 snap → 厚度回填
  rooms.ts                  封洞 + connectedComponents → 房间多边形
  wallNet.ts                M5.1 墙网闭合（跨洞合墙 / 悬空端点闭合，纯 TS）

  columns.ts                M5 柱候选（近正方形实心块）

  debug.ts                  过程可视化（每步 mask 渲染成 PNG dataURL）

src/ai/fuse.ts              M4 融合器：CvExtract + RecognizeResult → SolveResult

```

## 2. CV 管线（对日式間取り图的适配是重点）

`extractGeometry(image, opts) → CvExtract`：

```ts
interface CvExtract {
  walls: Array<{ x1: number; y1: number; x2: number; y2: number; thicknessPx: number }>;  // 像素坐标中心线
  rooms: Array<{ polygon: PxPoint[]; areaPx: number }>;
  // M5 新增：
  openings: Array<{ x1; y1; x2; y2; onWallIndex?: number; exterior: boolean }>;  // 墙上的缺口中心线段
  columns: Array<{ x; y; wPx; hPx }>;                                            // 近正方形实心块
  deskewDeg: number;          // 应用过的旋转校正
  stats: { wallStrokePx: number /* 墙笔画中位宽 */, mode: 'clean' | 'photo' };
  warnings: string[];
}
```

1. **binarize**：灰度 → 判定模式（直方图双峰性判断 clean/photo）→ clean 用「近黑固定阈值」（避免 Otsu 把房间填色划进来）、photo 用 `adaptiveThreshold`；`HoughLines` 主方向 deskew（±5° 内才转）
2. **wallMask**：`morphologyEx(MORPH_OPEN)` 只留粗笔画（kernel 按墙笔画宽自适应：`distanceTransform` 中位数估 DPI）→ `connectedComponentsWithStats` 按面积/长宽比/填充密度剔除日文文字块与尺寸线 → **虚线链剔除（M4.1，见第 6 节）** → `MORPH_CLOSE`（kernel < 门宽，别把门洞封死）→ **细线框剔除（M4.1）**
3. **skeleton**：Zhang-Suen 细化得 1px 中心线（opencv.js 没有 ximgproc.thinning，自写）
4. **segments**：`HoughLinesP` → 与 0°/90° 偏差 ≤10° 的量化到轴向、**其余保留原角度**（斜墙约定与 M3.1 一致）→ 共线合并（角度+偏移分组）→ 端点聚类 snap（T 型接点闭合）→ 厚度 = 该段沿线的 distanceTransform 中位数×2
5. **rooms**：**孤岛墙段剔除（M4.1）** → `cornerHarris` 找端点沿轴补线封门洞 → `connectedComponents` → 面积过滤（> 0.2 帖对应像素，M4.1 从 0.25 帖放低）→ `findContours + approxPolyDP` 出房间多边形

## 3. 融合器（src/ai/fuse.ts）

输入：`CvExtract` + VLM `RecognizeResult`（语义）+ 图片尺寸。输出与 `solveRecognizeResult` 同型（`SolveResult`），UI/applyRecognition 零改动。

1. **比例**：优先「VLM 帖数 ∑ ÷ CV 房间像素面积 ∑」→ mm/px（CV 面积精确，比 VLM 多边形可靠）；无帖数退回 VLM 的 drawingWidthMm
2. **墙**：CV 线段 ×(mm/px) → 轴向端点 455 吸附、斜墙端点 100 吸附（沿用 M3.1 常量）→ Wall[]
   - 阶段 A 的三个遗留项在这一步收口：**图片外框线**（贴图边 + 沿该边并集跨度 ≥ 80% → 丢弃）、
     **短斜段噪声**（< 600mm 的斜段丢弃）、**厚度偏大**（`distanceTransform` 的结果 ×0.8 再用来推导容差）
   - 轴聚类用 `buildAxisMap(..., { onCollision: 'merge' })`：CV 一张图能吐几十条精确坐标，
     纯 VLM 路径那套「撞格就错开一格」会把图纸一格一格撑大（实测面积虚增近 30%）
3. **房间语义挂载**：VLM 房间中心（归一化→px）落在哪个 CV 房间多边形内 → 挂 name/floor/tatamiCount；一对多/无匹配记 warning（CV 房间无语义 → name「房间」，VLM 房间无宿主 → **先试 IoU 兜底（M4.1）**，仍失败才丢弃并警告）。融合后**面积 < 1.5 帖的无名碎块并进公共边最长的具名邻居（M4.1）**
4. **门窗**：VLM openings 投影到 CV 墙段（复用 placeOpenings）；**柱**沿用 VLM（后续可加 CV 实心块检测）
5. **帖数校验**：沿用 M3.1 的 25% 偏差警告（现在偏差大多来自 CV/比例，可信度更高）
6. **underlay 对齐**：mmPerPixel 即比例，offset 由整体平移量反推（含 deskew 时把旋转角写进 underlay.rotation）

## 4. API / UI（阶段 B 已实现）

- `/api/recognize` 请求体加 `pipeline?: 'vlm' | 'hybrid'`，**默认 `hybrid`**。hybrid：CV 提取（本地，~1s）与 VLM 调用 `Promise.all` 并行，回来后 `fuseCvAndVlm` 融合
- **融合在服务端做**：响应多带 `solved`（融合好的 `SolveResult`）、`pipeline`（实际用的）、`cv`（提取统计）。
  前端拿到 `solved` 就不再跑本地 solver；`solved` 为 null（纯 VLM 路径）时行为与 M3 完全一致
- **自动回退**：CV 房间数为 0 或墙段 < 6（`MIN_HYBRID_WALLS`）→ 退回纯 VLM，响应里 `pipeline: 'vlm'` +
  warning「图纸提取失败（整版广告图请先裁剪出户型部分），已回退纯 AI 模式」。test1 这类整版广告图必走这条
- mock 模式（`MOCK_RECOGNIZE=1`）永远走纯 VLM——fixture 里没有真图，CV 无从提取
- **小隔间忽略（M4.2）**：请求体加 `ignoreSmallRooms?: boolean`，**默认 `true`**。
  低分辨率源图上 洗面所 / トイレ / 玄関 / WIC 这类隔间 CV 提不出连通域，VLM 房间挂载必然失败，
  以前每个都刷一条「已丢弃」warning。开启后这类房间**安静跳过**（判据见 `isSmallRoom`：帖数 < 3
  或名字命中 `SMALL_ROOM_NAME_PATTERNS`，NFKC 归一化后子串匹配），只计进 `fuseStats.ignoredSmallRooms`；
  **挂载成功的小隔间不受影响**，几何一条不变。传 `false` 恢复 M4.1 的丢弃 + warning 行为。
  test2 fixture 实测：warning 9 → 5 条（忽略 4 个小隔间）
- RecognizeDialog：「识别方式」下拉（AI + 轮廓提取（准）/ 纯 AI（快），初值取服务端的默认管线），
  hybrid 下多一个「忽略小隔间（洗面所・トイレ等）」勾选框（默认勾上），
  完成面板显示「N 墙段 / N 房间 · 比例 x mm/px」、「已忽略 N 个小隔间」与回退提示
- `server/test-recognize.mjs --pipeline vlm|hybrid|both`（`both` = 同图两条管线各跑一遍，对比表按「模型 · 管线」分列），
  `--keep-small-rooms` 关掉小隔间忽略
- **debug CLI**：`node server/cv-debug.mjs testdata/test2.jpg --out xxx/` 输出：原图叠加提取墙段（红线，粗细=厚度）+ 房间多边形（半透明填色）+ 各中间步骤 mask 的 PNG；
  `--full` 额外把完整的 walls/rooms 打成 JSON（`src/ai/fixtures/cvExtract-test2.json` 就是这么来的）

## 6. M4.1：虚线剔除 + 语义抢救

### 6.1 病根

**間取り图上的虚线从来不是墙。** LDK 里那个虚线矩形是**床暖房（地暖）的铺设范围**；
其余虚线是梁、吊柜投影、上层轮廓、可动间仕切りの軌道。M4-CV 的管线把它们当墙提，
于是 test2 的 LDK 被地暖框的上边横切成两半 —— 「厨房带」和「客厅」各成一块，
帖数标注 15.5 帖去除以只有一半的像素面积，**比例（mm/px）整个偏大 12%**，
一连串无名小房间也是这么冒出来的。

### 6.2 三道新工序

| 工序 | 位置 | 模块 | 判据 |
| --- | --- | --- | --- |
| 虚线链剔除 | 文字剔除同阶段，**闭运算前** | `cv/dashFilter.ts` `findDashChains` | 短小（长边 < 3× 墙笔画宽）+ 细（短边 < 0.8×）+ **沿同一直线等间距重复 ≥3 个** → 整链剔除 |
| 细线框剔除 | **闭运算后、开运算前** | `cv/dashFilter.ts` `pickThinComponents` | 连通块的代表厚度（`distanceTransform` 的 p90×2）< 0.6× 墙笔画宽 → 整块剔除 |
| 孤岛墙段剔除 | 墙段提取后、**房间提取前** | `cv/islandFilter.ts` `dropIslandWalls` | 与主墙网不连通 + 落在图纸内部（或某 CV 房间里）+ 平均厚度 < 0.6× 厚度中位数 |

三条都**不写死像素**，全部由 `distanceTransform` 估出来的墙笔画宽推导。

两个跟规格不一样、但是跑真图跑出来的关键决定：

1. **细线框剔除必须在闭运算之后**。墨迹阶段的内墙本来就是「两条细线夹白芯」，
   自己也很细；闭运算把白芯填实之后「墙 = 粗、示意线 = 细」才成立。
   实测 test2：地暖框闭运算后代表厚度 5.8px、内墙 11px+、墙笔画宽 11.5px，一刀切得干干净净。
2. **低分辨率图上 `findDashChains` 一条都找不到，真正干活的是细线框剔除**。
   网上抓的 500px 宽小图，虚线在**源图分辨率上就已经糊成一条连续细线**了
   （test2 的地暖框：灰度 232 的连续线，放大到 1200px 宽后 6px 粗）——
   「找一杠一杠」根本无从找起，只能靠粗细分辨。`findDashChains` 留着是给高分辨率图用的。
3. **孤岛剔除必须在房间提取之前**：孤岛本身就会把房间切开，等房间出来再删就晚了。
   所以 `pipeline.ts` 跑**两遍** `extractRooms`：第一遍只为拿到「孤岛落在哪个房间里」的判据，
   剔完再正式跑一遍（纯连通域，开销可忽略）。

`extractRooms` 的最小面积也从 0.25 帖放低到 **0.2 帖**（碎块下限 `stroke²×6 → ×4`）：
トイレ / 洗面所 / 収納 这些小间本来就在 0.5~1 帖，门洞封得不完美时轮廓会缩水。

debug 叠加图里：**蓝框 = 文字块，黄框 = 虚线链 / 细线框**。

### 6.3 融合器的两条语义抢救（`ai/fuse.ts`）

- **IoU 兜底**：VLM 房间的中心点挂不上宿主时（凹房间、VLM 轮廓画偏、CV 把房间切碎），
  改比「VLM 多边形 ∩ CV 区域」的 IoU，> 0.3 的最大者收留它。
  中心点命中永远压过 IoU 兜底（`Claim.kind` 排序）。
  IoU 用**网格采样**算（96×96）：CV 房间是凹多边形，Sutherland–Hodgman 那类算法靠不住，
  而这里只要判「是不是大致同一块地方」。
- **无名碎块合并**：面积 < 1.5 帖的**无名**区域，并进与它**公共边最长**的具名邻居。
  合并是真正的多边形并集（`unionAdjacentPolygons`）：两块取同一绕向 →
  把**反向共线且重叠**的边段成对抵消 → 剩下的边首尾相接串成一个环。
  直角多边形（矩形 / L 型 / 带阶梯）全吃得下，也不会像凸包那样把中间的墙吞进去；
  拼不出单个环、或面积对不上（差 > 2%）就放弃，原样保留两块。

### 6.4 test2 实测（M4-CV → M4.1）

| | M4-CV | M4.1 |
| --- | --- | --- |
| CV 墙段 / 区域 | 68 / 9 | 64 / 8 |
| LDK | **被切成两块**（下半 15.5 帖标注 ÷ 半块面积） | **完整一块** |
| mm/px | 37.27 | **33.32** |
| 帖数一致性 | LDK 1729 mm²/px vs 洋室① 1094 —— 差 58% | LDK 1100 / 洋室① 1094 / 洋室② 1161 —— **1% 内** |
| 融合后 LDK 面积 | 8.1 帖（标注 15.5） | **15.3 帖**（标注 15.5） |

剔除统计：虚线链 0 条、细线框 2 块（地暖框 + 一块家具轮廓）、孤岛墙段 6 段（4 团）。

回归（墙段 / 区域，M4-CV → M4.1）：test1 14/0 → 14/0（仍回退纯 VLM）、
test3 40/5 → 38/7、test4 65/9 → 65/10、test5 64/10 → 64/13。
墙段波动 ≤ 6%，叠加图目检无缺墙；区域数上升来自最小面积放宽（意料之中）。

**仍未解决**：test2 的 洗面所 / トイレ / ウォークインクローゼット 依旧提不出区域 ——
它们之间的隔墙在 500px 源图上只有一两像素的浅灰，二值化后就断了，
属于源图分辨率的下限，不是算法能救的（换高清图即可）。

## 7. 已知风险（M4 时列的，M5 仍然有效）

- test1 这类整版广告图：CV 会把版面装饰线/照片边框当墙 → 需要「最大连通墙体团」启发式（取包含最大房间集合的连通分量）；仍失败就要求用户先裁剪（UI 提示）
- 照片翻拍（透视畸变非仿射）：deskew 只处理旋转，梯形畸变不管——先记 warning，效果差再加透视校正
- opencv.js 在 vitest(jsdom) 里加载 WASM 可能慢：CV 步骤的测试走 node 脚本跑真实图，vitest 只测纯 TS 几何

## 8. M5：CV 唯一几何源 + AI 纯标注（**当前架构**，已实现）

### 8.1 管线

```
图片 → src/cv extractGeometry（墙 / 房间 / 洞口候选 / 柱候选，全部像素坐标）
     → 达标校验（房间 ≥ 2 且墙 ≥ 6，否则直接抛 cv_insufficient，不再回退 AI 画几何）
     → server/markedImage.mjs 生成「编号标记图」（房间锚点上画白底黑字圆标；画不了则退化成文字清单）
     → AI 标注调用（原图 + 标记图）：对每个编号回答 {name, floor, tatamiCount, sameRoomAs}
     → src/ai/labelFuse.ts：比例 = Σ帖数 ÷ Σ对应 CV 房间像素面积 → CV 几何 ×比例 → 吸附
     → SolveResult（underlay 对齐同前）
```

新增 / 改动的文件：

| 文件 | 作用 |
| --- | --- |
| `src/cv/openings.ts` | 洞口候选（缺口 → `CvOpening`，含内外墙判定与去重） |
| `src/cv/columns.ts` | 柱候选（形状判据 + 贴墙判据，分两阶段跑） |
| `src/cv/anchor.ts` | 房间标签锚点（**保证落在多边形内部**） |
| `src/ai/cvGeometry.ts` | `fuse.ts` / `labelFuse.ts` 共用的「CV 几何 → mm」（外框过滤 / 轴吸附 / 墙合并） |
| `src/ai/labelSchema.ts` | 标注 schema + 校验 / 清洗 + `sameRoomAs` 归组 |
| `src/ai/labelFuse.ts` | M5 融合器 |
| `server/markedImage.mjs` | 编号标记图 / 文字清单 |
| `server/labelPrompt.mjs` | 标注 prompt |
| `server/providers/openrouter.mjs` | 加 `labelWithOpenRouter`（同一 provider / 模型 / 降级 / 重试策略，**无 refine**） |

### 8.2 关键决策与实测

1. **AI 零坐标输出**。标注 schema 是
   `{notes, rooms: [{index, name|null, floor, tatamiCount|null, sameRoomAs|null}]}`。
   坐标约定 / 多边形重叠 / 房间漏画这一整类 bug 从机制上消失了。
   实测成本：test2 一次 $0.0052、test5 一次 $0.0068。

2. **洞口的真正来源是「共线合并时被跨过的缺口」**，不是封房间的桥接段。
   `extractSegments` 为了让门洞两侧保持同一道墙，会跨过一个门宽以内的缺口
   （`mergeCollinearWithGaps` 现在把这些缺口一并吐出来）——**被跨过去的那一段就是门 / 窗**。
   只用 `planBridges` 的桥接段的话，实测 test2 的 9 个候选里 8 个不足 500mm：真门洞早被合并掉了，
   剩下的全是碎片。改用合并缺口之后 test2 的候选 9 → 19、test5 13 → 28。

3. **洞口类型启发式**：外墙缺口 = window，内墙缺口 = door。「外墙」的判据是
   *贴着所有墙的包围盒边缘* **或** *法向两侧都不在任何 CV 房间里*。
   刻意**不用**「有一侧不在房间里就算外墙」——低分辨率图上 CV 分不出洗面所 / トイレ，
   那条判据会把一半的内门判成窗（实测 test2：9 个缺口里 7 个被误判成外墙）。

4. **洞口 / 柱必须走与墙**同一条**坐标变换**（`transformNormPoint`：×mmPerPx → `applyAxis` → 平移）。
   只做 `×mmPerPx + 平移` 会整体错位：轴聚类 + 455 吸附是分段线性映射，一张图能累积出上千毫米。
   实测漏掉这一步时 test2 的候选**一个都放不进墙里**。

5. **柱**（尽力而为）：近正方形实心块（边长 0.5~2× 墙笔画宽、填充率 > 0.85）在 `wallMask` 的文字剔除
   阶段就记账（**不进 mask**，避免实心块细化出噪声墙段），等墙段提完再按「离最近墙段 < 1× 笔画宽」筛一遍。
   实测 test1~test5 只在 test3 抓到 1 根——识别不出就空数组，不硬凑。

6. **`sameRoomAs` 是比例正确性的命门**。吧台 / 垂れ壁会把一个房间切成好几块，
   AI 会老老实实给每一块都写上同一个帖数；不归组的话帖数被算三遍，
   **整张图大出七成**（test5 实测：101.5 帖 → 归组后 40.3 帖，后者才是这套 3LDK 的真实量级）。
   归组之后帖数每组只算一次、面积按整组求和；几何上再用 `unionAdjacentPolygons` 尝试把碎块拼回一间，
   拼不上就保留碎块并**清掉该组的帖数标注**（否则每块都会刷一条「面积与标注偏差 60%」的假警报）。

7. **CV 不达标即报错**（房间 < 2 或墙 < 6 → `cv_insufficient`，HTTP 422），**不再回退 AI 画几何**。
   前端弹「这张图没法自动提取户型」+ 一键「把这张图设为底图并手动描摹」。
   这条路径**不花任何 API 费用**（错误在标注调用之前抛出）。

8. **识别用的图不能被无谓地重编码**（浏览器侧，`prepareRecognizeImage`）。
   M4 时前端一律走 `compressImageFile`（canvas + JPEG quality 0.8）。几何还是 VLM 出的时候
   这没什么影响；M5 把几何交给 CV 之后，多出来的那一圈 JPEG 振铃会把细内墙打断，
   **实测 test2：原始字节提出 8 块区域（含 15.5 帖的 LDK），重编码后变成 11 块碎区域、LDK 那一整块直接消失**。
   现在尺寸与体积都在预算内的图**原样送走**（間取り图基本都是这一类），只有确实过大的才压。

9. **标注挂载天然免疫低分辨率语义丢失**：AI 按编号回答，不存在「中心点落不进区域」的问题。
   `ignoreSmallRooms` 那套补丁在 M5 里失去意义（API 字段保留兼容，UI 勾选框已移除）；
   `hybrid` / `vlm` 管线保留在 API 与 `test-recognize.mjs --pipeline` 里供对比，**UI 不再暴露**。

### 8.3 opencv.js 的绘制能力（实测结论）

`@techstark/opencv-js` 5.0 的默认 WASM 构建：

| API | 有没有 |
| --- | --- |
| `putText` / `circle` / `rectangle` / `line` / `fillPoly` / `resize` / `cvtColor` | ✅ |
| `getTextSize` | ❌ 字号只能按 Hershey 字体的固有度量估（步进宽 20px、字高 21px @ scale 1） |
| `imencode` | ❌ PNG 编码走 pngjs（`src/cv/decode.ts` 的 `encodePng`） |

所以**走的是标记图这条主路**。源图不足 1400px 宽时先放大（上限 3×），
否则 500px 宽的图上圆标只有几个像素，模型根本读不清。
`buildMarkedImage()` 返回 `null`（构建里没有 `putText`、或一块区域都没有）时自动退化成
`roomListText()` 的文字清单（编号 + 归一化重心 + bbox + 占图面积比），prompt 会切换成对应的说法。

**两张图都要发**：标记图上的圆标会盖住房间名文字（test2 的 2 号圆标正好压在「洋室①」上），
所以 prompt 明确要求「在标记图上确认编号位置，回原图读文字」。

### 8.5 已知局限

- **洞口宽度受两处「一个门宽」的上限约束**（`mergeCollinearSegments` 的 `gapTolPx = 6× 笔画宽`、
  `planBridges` 的 `maxDoorGapPx ≈ 900mm`），所以 1650mm 以上的引き違い戸提不出来。
- 低分辨率图上缺口普遍量小（见上），洞口召回率随分辨率显著变化。
- ~~碎块拼回依赖 `unionAdjacentPolygons` 的「共享边抵消」，而 CV 的两块区域之间隔着一整条墙带，
  多数情况下拼不上（test5 只拼回了 2 组 / 5 组）~~ → **M5.2 已修**（第 10 节）：
  摘掉吧台隔断 + 栅格搭桥之后 test5 的三块 LDK 拼成了一间。拼不上时仍然退化成
  「同名多块 + 无帖数」，不产生错误几何。
- 柱检测只能抓**独立画出来的**实心方块；与墙连成一体的柱型本来就不是独立连通块。
- `cv` 管线目前**只支持 OpenRouter provider**（Anthropic 路径没有对应的标注实现）。

## 9. M5.1：墙网闭合 + 装饰图形剔除（**当前架构**，已实现）

M5 的渲染结果暴露出两个病：**悬空线头到处都是**、**指北针被当成墙**（test5 的指针成了一条竖线）。
三道新工序全部插在 `pipeline.ts` 的**房间提取之后**（轮廓要拿房间/墙网来定，跨洞合墙要拿
`planBridges` 的缺口来定），三步都会重排墙段下标，所以桥接段的下标映射一路 `composeIndexMaps` 复合过去。

| 工序 | 模块 | 判据 |
| --- | --- | --- |
| 建筑轮廓外剔除 | `cv/outline.ts` `buildBuildingOutline` / `dropOutsideWalls` | 三个采样点（两端 + 中点）都落在建筑轮廓外 → 剔除 |
| 跨洞合墙 | `cv/wallNet.ts` `mergeWallsAcrossGaps` | `planBridges` 认成 `gap` 的缺口，两侧共线墙并成一条 |
| 悬空端点闭合 | `cv/wallNet.ts` `closeDanglingEnds` | 自由端 → `max(1.5× 墙厚, 250mm)` 内延伸到最近墙体（T 接）；够不着且两端都自由、短于 600mm → 碎屑丢掉 |

### 9.1 跨洞合墙：洞口是 Opening，不是墙的断点

`extractSegments` 的 `mergeCollinearWithGaps` 只跨得过 `6× 笔画宽` 的缺口，比这更宽的门 / 引き戸
就把一道墙劈成两段，于是门洞两侧各留一个悬空线头。可 PlanDoc 的模型里洞口是**挂在墙上的
Opening**（`wallId + offset`），墙本身是连续的 —— 所以凡是 `planBridges` 认成 `gap` 的缺口，
两侧都合成一条连续墙。**被丢弃的候选（宽度不合理）也照合不误**：那本来就是骨架断裂，更不该留断墙。

合并方式是「组内长度加权拟合一条直线 → 端点投影 → 取区间两端」，厚度按长度加权平均；
链式的（A—洞—B—洞—C）会并成一条。洞口的 `offset` 不用管：`labelFuse` 的 `placeCvOpenings`
本来就是在 mm 空间重新 `nearestWall`，自然落到合并后的那道墙上。

### 9.2 建筑轮廓：用「主墙网围出来的面」，不是房间并集

装饰图形（指北针 / 图例 / 比例尺 / 家具示意）有一个雷打不动的共同点：**永远在建筑轮廓之外**。
M4.1 的孤岛剔除要求「比墙细」，test5 的指北针指针是个实心三角，够粗，就这么逃掉了。

轮廓的定义踩了三个坑，都是跑真图跑出来的：

1. **不能只用房间并集**。低分辨率图上 CV 分不出的 洗面所 / トイレ / 廊下 在房间并集里是一整片
   空白，而且顺着玄関一路通到图外（不是封闭的洞，填洞救不了）—— 实测 test2 会**误杀 8 段真内墙**。
   改成「把主墙网 + 封洞桥接段栅格化，再从图边洪水填充，填不到的格子就是建筑内部」，这些夹缝立刻全归位。
2. **只能用主墙网**（`islandFilter.findWallIslands` 的最大连通子图）。图框线是独立孤岛：
   算进去的话「图框与建筑之间那一圈」会被判成建筑内部，贴着图框画的指北针（test2）就逃掉了。
3. **门洞必须先封上**（`sealSegments` 传 `extractRooms` 的 bridges），否则洪水填充顺着门口灌进屋里，
   整栋楼都算成外部。

算完再向外扩 1× 墙厚。实现是**栅格**（默认半个墙厚一格，1200×900 上也就 400×300 格）而不是
多边形布尔运算：房间是凹多边形还可能自交，栅格化 + 洪水填充 + 膨胀既简单又稳。
debug 叠加图里 **品红框 = 轮廓外剔除的墙段**，`__steps.png` 多了第 5 张图就是轮廓本身。

### 9.3 悬空端点：延伸要大方，丢弃要保守

`closeDanglingEnds` 只有一条延伸规则（沿自身方向到两条直线的交点，且交点必须落在对方墙**身上**、
不许把线段拉过头），丢弃规则则刻意保守：**两端都还悬空 + 短于 600mm** 才算碎屑。
阳台矮墙、开放边界都是合法的自由端，宁可留着记一条「还有 N 处墙端没有闭合」的 warning。

试过再加一轮「两个自由端点互相吸到拐角交点」的角点闭合，test2~test5 上**一个都没多闭合**
（剩下的自由端确实都是孤零零的），代码就没留。

### 9.5 M5.1 的已知局限

- **悬空端点消不到 0**：剩下的（test2 24 / test5 17）多数是阳台矮墙、开放边界这类**合法**自由端，
  少数是低分辨率区域里的孤立残段。判据一旦放松到能全清，就会开始吃真墙。
- **轮廓外剔除会顺手清掉「CV 分不出的小间里的孤立残段」**（test2 的 洗面所 / WIC 各一小段）。
  那些本来就是断头线，清掉反而少几个悬空线头，但确实是几何信息的损失。
- 图框线**紧贴建筑**（两者连成一个连通分量）时，轮廓会把图框内的整圈算进建筑，
  贴框画的装饰就逃掉了 —— 这是刻意选的 fail-safe 方向（宁可漏剔，不可误杀）。
  这种图仍然靠 `cvGeometry.dropBorderWalls` 在融合阶段兜底。

## 10. M5.2：同房间碎块拼合（**当前架构**，已实现）

M5 的 `sameRoomAs` 已经能让 AI 正确指出「这几块 CV 区域其实是同一间房」，比例也按组只算一次了，
可**几何拼不回去**：test5 的三块 LDK 到 M5.1 为止仍然各自带一个标签（见 8.5）。
病根很具体——`unionAdjacentPolygons` 走的是**共享边抵消**，而被吧台 / カウンター 切开的两块之间
隔着一整条**墙带**（test5 实测 455mm），一条共享边都没有，抵消不出任何东西。

新增文件：`src/ai/roomMerge.ts`（假隔断判定 + 栅格拼合）、`src/ai/wallRepair.ts`（摘墙后补墙网），
两者都是纯函数、纯 mm 域、不 import opencv。

### 10.1 三步：判假隔断 → 摘墙搭桥 → 栅格拼合

| 工序 | 模块 | 判据 |
| --- | --- | --- |
| 假隔断判定 | `ai/roomMerge.ts` `findFakePartitions` | 沿墙 5 个采样点、法向两侧各一根探针；两侧都落进**本组不同的碎块** → 吧台 / 家具隔断 |
| 桥接带 | `ai/roomMerge.ts` `sweepBridge` | 沿墙每 100mm 一个样点，宽度按**该点实测**的落点距离给；沿墙**往两头长**到两侧不再都是本组为止 |
| 栅格拼合 | `ai/roomMerge.ts` `rasterMergePolygons` | 碎块 + 桥打到 50mm 网格 → 填洞 → 去对角夹点 → 连通域 → 边界跟踪 → RDP → 顶点吸附 |
| 局部补墙网 | `ai/wallRepair.ts` `repairWallNet` | 复用 `cv/wallNet.ts` 的 `closeDanglingEnds`（mm 域），**只修被摘墙段附近**的残端 |

拼合仍然是**两级**的：先试 `unionAdjacentPolygons`（两两试到并不动为止，比 M5 那种
「按代表块串着并」稳——test5 的 LDK 里 #1 跟 #2/#4 都不相邻，可 #2 跟 #4 是相邻的），
剩下的块才走摘墙 + 栅格这条路。拼合后的房间**语义取面积最大的那一块**（大块被 AI 标错名字的概率最低）。

### 10.2 探针为什么这么设计

- **起点 `0.8×墙厚 + 50mm`**：先跨过墙体本身再开始找房间。
- **步进 25mm、最远 910mm（两个半格）**：CV 的墙带被 455 网格吸附之后普遍是 455mm 宽，
  探针必须够得着对面那一块；再远就会跨过整间小屋。
- **「第一个撞到的房间」才算数**：这是整套判据安全的关键。`probeMax` 给得再大，探针也会
  先撞上最近的那间屋——想穿过一间屋去够到组内的另一块是不可能的。
- **候选 / 真墙的分野**：只有「两侧分别是本组**不同**碎块」的墙才是候选。
  候选墙只要有任何一个采样落在**组外房间**或**建筑外**（探不到任何房间），就判成真墙：
  **不摘，整组放弃拼合**并 warning「…的碎块之间存在共享墙，已保留分块」。
  只有一侧是本组、另一侧是别处的墙是这一组的**外墙**，既不是候选也不影响结论——
  不做这个区分的话每一组都会被自己的外墙一票否决。

**桥要沿墙往两头长**，这一条是跑真图跑出来的：CV 往往只在墙带中间提出一小截墙段
（test5 的吧台只覆盖 1820mm，而两块碎块之间的整条缝有 3640mm），
不往外长的话拼出来的 LDK 会留两个 455mm 深的豁口。往外长到「两侧不再都是本组」自然会停，
天然停在墙带的尽头。

### 10.3 栅格拼合的取舍

选栅格不选多边形布尔运算，理由跟 `cv/outline.ts` 建筑轮廓那次一样：碎块是**凹多边形、可能自交**，
桥接带又会跟碎块**大面积重叠**——这正是「共享边抵消」处理不了的形状。栅格化 + 洪水填充又简单又稳。
代价与对策：

- **50mm 量化**：面积误差量级 ≈ 周长 × 25mm，test5 的 LDK 上是 0.5% 以内。
- **斜边会被切成台阶**：先跑一遍 RDP（容差 1.5 格），台阶压回直线。
  不做这一步 test5 的 LDK 是 **50 个顶点**，做完是 **13 个**。
- **顶点抖动**：吸附回「碎块 / 桥本来就有的坐标」（容差 60mm）。而且**按边吸不按点吸**——
  近水平的边把两端的 y 拉成同一个、近垂直的边拉 x，斜边的端点只由它另一侧那条轴向边定坐标。
  挨个顶点独立吸 x/y 的话，斜边中间会被拽出一截 140mm 的假水平段（实测过）。
- **对角夹点**：2×2 里只有一对对角实心时边界会自交，补一个 50mm 的格子消掉。
- **内部空洞**：洪水填充填不到的空格子一律补实——房间轮廓只能是一个环，带洞的多边形下游画不出来。
- **连通域 > 1 就返回 `null`**：桥没搭上时**保留碎块**，不硬拼；那一组记一条 warning。
  这一条和「探到真墙就整组放弃」是这一版仅有的两个失败出口，两个都退化成 M5.1 的行为。

### 10.4 摘墙之后必须补墙网

摘掉一条隔断，原本 T 接在它身上的墙端就会变成悬空线头——M5.1 刚把悬空端点从 41 压到 17，
这一版**不能让它复发**。`repairWallNet` 复用 `cv/wallNet.ts` 的 `closeDanglingEnds`：
那套判据本来就是**域无关**的（名字里的 `Px` 是历史包袱，实现里从没假设过单位），
mm 域只要把 `pxPerMm` 传 `1` 就行，两处的单测都在。

**只修局部**：只有端点落在「被摘墙段一道墙厚以内」的墙才允许被延伸 / 当碎屑丢掉，
其余原样保留——不这样限制的话，凡是有 `sameRoomAs` 组的图整个墙网都会被重跑一遍，
改动范围远超这次修复的意图。另外**没摘墙就整段跳过**，所以没有 `sameRoomAs` 组的图
（test2）这一步一行代码都不执行。`labelStats` 里新增 `fakePartitionsRemoved` /
`danglingEndsBeforeMerge` / `danglingEndsAfterMerge` 三个数，摘墙反而多出悬空端点时会直接报警。

### 10.6 M5.2 的已知局限

- **碎块之间没有 CV 墙段时拼不了**。test5 的 主寝室（3+6）、洋室（7+8）之间那条缝
  CV 一段墙都没提出来（被当成文字块 / 家具线剔掉了），没有「假隔断」可摘也就没有桥可搭，
  仍然退化成「同名两块 + 无帖数」。要救得改成「按缝隙本身搭桥」，而那条路子少了
  「摘墙即证明这是假隔断」这道安全闸，会开始误并真隔壁的房间——这一版刻意没做。
- **バルコニー（5+12）判成了「有共享墙」**：那两块之间隔着建筑角，探针探到室外，
  判据正确地拒绝了拼合。想合并只能手动。
- **拼合出来的多边形不再与原碎块顶点严格重合**（量化 + 吸附各 ±50mm 量级）。
  相邻房间的边界因此可能出现几十毫米的缝——不影响面积与显示，介意的话手动对齐。
- 假隔断判定跑在**吸附之后**的 mm 空间，455 网格造成的墙带宽度误差 910mm 的上限已经覆盖；
  真出现比这更宽的墙带（超厚承重墙 + 高分辨率图）会拼不上。
- **房间里横穿的墙不摘**：两侧落在**同一块**碎块里的墙（test5 的 LDK 上就有一条）不算候选，
  照旧留在成果里。那多半是柜台 / 垂れ壁的投影，摘不摘都有争议，交给用户删。
